THE APPLICATION FRAMEWORK FOR RUST

Enterprise Rust, in bloom.

Dependency injection, auto-configuration and starters — resolved by the compiler, not at startup. Familiar if you’ve built with Spring Boot; checked like everything else in Rust.

src/orders.rs 
#[component]
pub struct OrderService {
    repo: Inject<dyn OrderRepository>,
    events: Inject<EventBus>,
}

#[rest_controller]
pub struct OrderController { svc: Inject<OrderService> }

#[routes]
impl OrderController {
    #[get("/orders/{id}")]
    async fn show(&self, id: Path<Uuid>) -> Json<Order> {
        Json(self.svc.find(*id).await)
    }
}
// forget to provide OrderRepository?
// that's a compile error, not a crash at boot.
WHY OXBLOOM

The conventions you know. The guarantees you want.

Wired at compile time

Components and their dependencies are resolved by macros during the build. No reflection, no classpath scanning, no startup surprises.

Starters, not boilerplate

Add oxbloom-starter-web or -data and get sensible defaults you can override one by one.

Configuration that type-checks

Profiles and properties map onto typed structs. A typo in application.toml fails the build, not production.

Production from day one

Health checks, metrics and graceful shutdown come built in, so day two looks like day one.

COMING FROM THE JVM?

Oxbloom borrows the ideas that made Spring Boot productive and moves them to where Rust is strongest: the compiler.
