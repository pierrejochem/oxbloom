# oxbloom-di v2 design (slice C1: traits, collections, lifecycle, beans, profiles)

Date: 2026-10-24

## Purpose

Lift the limits that Slice 3 left in `oxbloom-di`: a component can provide and receive trait objects, collections and optional dependencies, beans have a lifecycle with ordered shutdown, beans can be created lazily, third-party types and computed values can be registered through typed factory functions, and registrations can depend on the active profiles. This is slice C1 of `docs/ROADMAP-core.md`. It is one slice made of three parts that share one registration model: (1) trait and collection injection, (2) lifecycle and lazy beans, (3) bean factories and profiles.

## Scope

In scope:

- `Arc<dyn Trait>`, `Vec<Arc<T>>` and `Option<Arc<T>>` as injectable shapes, with `primary` and `order`.
- Trait provision declared by `#[component(provides(..))]` or by a builder method.
- `Lifecycle` (`post_construct`, `pre_destroy`), `Container::shutdown`, lazy beans, a dependency depth limit.
- `.bean(f)` and `.try_bean(f)` (arity-generic), `#[configuration]` and `#[bean]`.
- Profile conditions on registrations, with the active profile names given to the builder.
- Unit structs for `#[component]`; clearer macro errors; `DiError` becomes `#[non_exhaustive]` with new variants.
- Small touch points: `oxbloom-web` `AppError::source`, `Config::active_profiles`, documentation.

Out of scope:

- Transient and request scopes; configuration injection by property key (`@Value`); conditions other than profiles (that is slice C4); constructor injection by name or qualifier; circular-dependency support through proxies.
- `#[bean]` on free functions and generic `#[configuration]` impls.
- Automatic shutdown in `Drop`; async lifecycle hooks.

## Decisions

- One internal model: a typed provider index. Every registration is an entry with a concrete key and zero or more provided keys. Resolution of any shape (single, optional, collection) works on the same index.
- Traits are provided explicitly, never discovered: `#[component(provides(dyn T))]` or `.provides(|a: Arc<Impl>| -> Arc<dyn T> { a })`. The closure body is the identity and the unsizing coercion happens at its declared return type, which is why it cannot be written generically on stable Rust. The closure names the concrete type, because the builder cannot infer the type of its last registration at compile time; the builder checks at `build()` that it matches the last registered entry (otherwise `Invalid`).
- Several providers for one single `Arc<dyn T>` is an error unless exactly one is `primary`. The container never picks silently.
- Lifecycle uses a `Lifecycle` trait plus builder closures, not method attributes.
- Bean factories come both as arity-generic builder methods and as `#[configuration]` / `#[bean]`.
- Profile conditions take names, any-of lists and negation. The container does not depend on `oxbloom-config`; the application passes the names.
- Runtime container remains the design (no compile-time graph proof).

## Public API

### Keys and shapes

A key is a type: a concrete `T`, or `dyn Trait`. A provided trait must be `Send + Sync + 'static` (`trait Notifier: Send + Sync`).

Injectable shapes, usable as `#[component]` fields, as `Resolver` methods and as `bean` parameters:

| Shape | Meaning |
|---|---|
| `Arc<T>`, `Arc<dyn T>` | exactly one provider, or the single `primary` provider; otherwise `Missing` or `Ambiguous` |
| `Option<Arc<T>>`, `Option<Arc<dyn T>>` | `None` when no provider exists; a provider that fails to create is still an error |
| `Vec<Arc<T>>`, `Vec<Arc<dyn T>>` | all providers, sorted by `order` then registration order; empty when none |

### Builder

```rust
impl ContainerBuilder {
    pub fn new() -> Self;
    // registrations
    pub fn component<T: Component>(self) -> Self;
    pub fn instance<T: Send + Sync + 'static>(self, value: T) -> Self;
    pub fn factory<T, F>(self, f: F) -> Self where F: Fn(&Resolver) -> Result<T, DiError> + Send + Sync + 'static, T: Send + Sync + 'static;
    pub fn bean<T, Args, F>(self, f: F) -> Self where F: BeanFn<Args, T>, T: Send + Sync + 'static;
    pub fn try_bean<T, Args, F>(self, f: F) -> Self where F: TryBeanFn<Args, T>, T: Send + Sync + 'static;
    pub fn configuration<C: Configuration>(self) -> Self;
    // modifiers: apply to the most recently registered entry
    pub fn provides<T, D, F>(self, coerce: F) -> Self where T: Send + Sync + 'static, D: ?Sized + Send + Sync + 'static, F: Fn(Arc<T>) -> Arc<D> + Send + Sync + 'static;
    pub fn primary(self) -> Self;
    pub fn lazy(self) -> Self;
    pub fn order(self, n: i32) -> Self;
    pub fn profile(self, name: &str) -> Self;          // any-of when repeated
    pub fn profile_not(self, name: &str) -> Self;
    pub fn post_construct<T, F>(self, f: F) -> Self where F: Fn(&T) -> Result<(), DiError> + Send + Sync + 'static;
    pub fn pre_destroy<T, F>(self, f: F) -> Self where F: Fn(&T) + Send + Sync + 'static;
    pub fn lifecycle<T: Lifecycle>(self) -> Self;    // registers both hooks of `T: Lifecycle` for the last entry
    // builder state
    pub fn profiles<I: IntoIterator<Item = S>, S: Into<String>>(self, active: I) -> Self;
    pub fn build(self) -> Result<Container, DiError>;
}
```

`factory`, `instance`, `component` keep their current signatures and meaning. `Component` gains a defaulted `fn configure(builder: ContainerBuilder) -> ContainerBuilder`, called by `component::<T>()` after the entry is pushed; the `#[component]` macro implements it to apply `provides`, `primary`, `order`, `lazy`, `lifecycle` and `profile` options. Builder methods never fail mid-chain: misuse (a modifier before any registration, a modifier whose type parameter does not match the last entry) is recorded and `build()` returns `DiError::Invalid`.

### Resolver and container

```rust
impl Resolver<'_> {
    pub fn get<D: ?Sized + Send + Sync + 'static>(&self) -> Result<Arc<D>, DiError>;
    pub fn get_opt<D: ?Sized + Send + Sync + 'static>(&self) -> Result<Option<Arc<D>>, DiError>;
    pub fn get_all<D: ?Sized + Send + Sync + 'static>(&self) -> Result<Vec<Arc<D>>, DiError>;
}
impl Container {
    pub fn get<T: ?Sized + Send + Sync + 'static>(&self) -> Result<Arc<T>, DiError>;
    pub fn get_opt<T: ?Sized + Send + Sync + 'static>(&self) -> Result<Option<Arc<T>>, DiError>;
    pub fn get_all<T: ?Sized + Send + Sync + 'static>(&self) -> Result<Vec<Arc<T>>, DiError>;
    pub fn shutdown(&self) -> ShutdownReport;
}
pub trait Lifecycle: Send + Sync + 'static {
    fn post_construct(&self) -> Result<(), DiError> { Ok(()) }
    fn pre_destroy(&self) {}
}
pub struct ShutdownReport { pub destroyed: usize, pub failures: Vec<DestroyFailure> }
pub struct DestroyFailure { pub type_name: String, pub message: String }   // fixed message text
pub trait Configuration { fn register(builder: ContainerBuilder) -> ContainerBuilder; }
```

`Container` stays `Send + Sync`.

### Macros

```rust
#[component(lifecycle, lazy, primary, order = 10, profile = "dev", provides(dyn Notifier))]
struct Mailer { transport: Arc<dyn Transport>, extras: Vec<Arc<dyn Extra>>, cache: Option<Arc<Cache>> }

#[configuration]
impl AppConfig {
    #[bean]
    fn pool(&self) -> Pool { .. }
    #[bean(fallible, lazy, primary, order = 1, profile = "!prod", provides(dyn Store))]
    fn store(&self, pool: Arc<Pool>) -> Result<MemStore, DiError> { .. }
}
```

- `profile` accepts one name, a list (any-of), or a name prefixed with `!`.
- `#[component]` fields may be any injectable shape; unit structs (`struct S;`) are accepted; `#[cfg]` attributes on fields give a clear error.
- `#[configuration]` goes on an inherent, non-generic `impl` and generates `impl Configuration`. Each `#[bean]` method becomes one entry that resolves `Arc<AppConfig>` and the method's other parameters, then calls the method. `fallible` states that the return type is `Result<T, DiError>`; no type sniffing. The bean key is the (inner) return type.
- All macros emit absolute paths (`::oxbloom_di::...`).
- Compile errors, with spans, for: generic or trait impls under `#[configuration]`, `#[bean]` outside a `#[configuration]` impl, methods without `&self`, parameters that are not injectable shapes, unknown or duplicate options, `provides` on a type that does not implement the trait, `#[component]` field types that are none of the shapes.

## Resolution and build

1. Profile filtering. Active profile names come from `.active_profiles([...])` (default none; renamed from `.profiles` during the final review). Before anything else each entry's profile conditions are evaluated: an entry is kept when it has no condition, or when any positive name is active, or when a `!name` condition names an inactive profile. A dropped entry is invisible: it is not a candidate, it cannot cause `Duplicate`, and a dependency on it is `Missing`.
2. Validation. Two kept entries with the same concrete type are `Duplicate { type_name, sources }`. Two providers of one trait are normal. Builder misuse recorded earlier becomes `Invalid`.
3. Eager creation. Kept, non-lazy entries are created depth-first in registration order. Creating an entry resolves its dependencies through the same index, so dependencies are created first. Each entry is created at most once.
4. Resolution of one key: candidates are the kept entries that provide the key. One candidate: used. Several, exactly one `primary`: that one. Several with none or several `primary`: `Ambiguous { requested, candidates }` (candidates are source labels). Optional and collection shapes follow the table above.
5. Cycles. The resolver tracks the in-progress concrete types; a repeated type is `Cycle { path }` as today (`A, B, A`).
6. Depth limit. The dependency depth along the resolver stack is capped at 256: deeper is `TooDeep { limit: 256, path }` with the path truncated to its first 8 entries.
7. Errors are cached per entry, except stack-relative ones. A creation that failed returns the same `DiError` for every later request of that entry and the provider is never run again. This closes the Slice 3 minor "a provider whose error was swallowed runs again". `Cycle` and `TooDeep` describe the requester's stack, not the entry, so they are never cached: a later request from another stack runs the provider again (an entry that can be built is never reported failed because it was first reached deep or through a cycle). The `required_by` and `path` of a cached `Missing`/`Creation` error describe the first requester.
8. Panics in providers and in `post_construct` hooks are not caught during `build()`; the panic propagates, as documented in Slice 3.

## Lifecycle, lazy beans, shutdown

- `post_construct` runs exactly once per bean, right after the instance is created and after the hooks of its dependencies; no dependent receives the bean before its hook has succeeded. A failing hook is `Creation { type_name, message }` and aborts `build()`.
- When `build()` fails after some beans were created, `pre_destroy` hooks of beans whose `post_construct` succeeded run in reverse creation order before the error is returned. The partial container is dropped.
- A lazy bean is created on first `Container::get*` or first injection. An eager bean that depends on a lazy one forces creation during `build()`. Errors in a lazy bean's creation (missing or ambiguous dependency, cycle, failing hook) appear at first use, not at `build()`.
- Lazy creation is serialized by one container-wide lock that is reentrant for the creating thread; the creation chain runs on that thread with its own resolver stack. Concurrent first access creates the bean once and the others wait. Two threads can never deadlock on each other's lazy chain, and cycles through lazy beans are reported as `Cycle`.
- `Container::shutdown(&self) -> ShutdownReport` takes the same lock and runs `pre_destroy` for every bean that was created, in reverse creation order (a lazy bean counts at the position where it was really created). A panicking `pre_destroy` is caught per hook and recorded as a `DestroyFailure` with fixed message text; shutdown continues. It is idempotent: a second call returns an empty report.
- After `shutdown`, every `Container::get*` returns `ShutDown` and no lazy bean is created. `Arc` handles already handed out stay valid.
- There is no implicit shutdown in `Drop` and no async hooks. The application lifecycle slice (C3) calls `shutdown` explicitly.

## Errors

`DiError` becomes `#[non_exhaustive]` and gains variants. All messages carry type names, source labels and fixed text; none carries a value. `Creation.message` is the developer's own text.

| Variant | Meaning |
|---|---|
| `Missing { requested, required_by }` | no provider for a required key (shape unchanged) |
| `Ambiguous { requested, candidates }` | several providers and no single `primary` |
| `Cycle { path }` | circular dependency (shape unchanged) |
| `Duplicate { type_name, sources }` | same concrete type registered twice; `sources` is new |
| `Creation { type_name, message }` | provider or `post_construct` failed (shape unchanged) |
| `Invalid { message }` | builder misuse |
| `ShutDown` | request after `shutdown()` |
| `TooDeep { limit, path }` | dependency depth over 256 |

Every entry has a source label for diagnostics: `Type::method` for `#[bean]` methods, `component Type`, `instance Type`, `factory Type`, `closure at file:line` for builder beans.

## Touch points in other crates

- `oxbloom-macros`: `#[component]` extended; `#[configuration]` and `#[bean]` added; re-exported through `oxbloom_di`.
- `oxbloom-web` (`di` feature): `AppError` implements `Error::source()`; `App::controller` is unchanged.
- `oxbloom-config`: `Config::active_profiles(&self) -> &[String]`, the final activated profile list after group expansion, so the application slice can pass it to `ContainerBuilder::profiles`. Documented and tested, no other change.
- `oxbloom-security` (`di` feature): `SecurityContainerExt` stays; a doc example shows `Vec<Arc<dyn AuthenticationProvider>>` injected into a `bean`. No restructuring.

## Compatibility

- Kept without signature change: `Component`, `ContainerBuilder::{new, component, instance, factory, build}`, `Container::get::<T>()` for concrete `T` (now also accepts `?Sized`), `Resolver::get`, `DiError::{Missing, Cycle, Creation}`.
- Changed: `DiError` is `#[non_exhaustive]`; `Duplicate` gains `sources`; `Container::get` after `shutdown` errors. Existing code that matches `DiError` exhaustively or destructures `Duplicate { type_name }` must be updated; the workspace crates are adapted in the same slice.
- Behavior: errors are cached per entry; resolution depth is capped at 256.

## Testing

All offline; each behavior has a failing-first test.

- Resolution: single trait provider; one entry providing concrete and trait; `primary` resolves ambiguity, none or two primaries give `Ambiguous`; `Vec` order (`order` then registration) and empty case; `Option` absent and `Option` with a failing provider; mixed shapes in a component and in a bean parameter list.
- Profiles: skipped entries are invisible (not candidates, no `Duplicate`); any-of and negation; no active profiles; dependency on a skipped bean is `Missing`.
- Lifecycle: hook order follows dependency order; failing hook aborts `build()` and runs `pre_destroy` of already-built beans in reverse order; `shutdown` order, idempotence, panicking `pre_destroy` caught and reported, `ShutDown` after shutdown, lazy beans destroyed only when created.
- Lazy: not created at build; created once under concurrent first access (threads plus a constructor counter); eager dependent forces creation; two threads with crossing lazy chains do not deadlock; cached failure returns the same error without re-running; cycle through lazy beans is `Cycle`.
- Beans: arities 0, 1 and 12; closure, `fn` item, `try_bean`; `#[configuration]` generating one entry per `#[bean]`; each option; `Duplicate` naming both source labels.
- Depth: a 300-deep chain gives `TooDeep` on a 256 KB-stack thread; a chain of 256 builds.
- Macro compile-fail (`trybuild`): the cases listed under Macros; unit structs compile; `#[cfg]` on a field.
- Compatibility: all existing DI, `oxbloom-web` `di` and `oxbloom-config` `di` tests pass, except pattern changes on `DiError` (listed in the task report). `Container: Send + Sync` stays a compile-time assertion.
- Hygiene: no `DiError` variant other than `Creation.message` contains developer text; a marker passed through factory messages appears only in `Creation.message`.
- Docs: doc examples for every public item per `AGENT.md`; README DI section rewritten; `docs/API.md` entries; `docs/ROADMAP-core.md` marks C1 done.

Done means: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets` and `cargo test --workspace` pass, each also with `-p oxbloom-web --features di`, `-p oxbloom-config --features di` and `-p oxbloom-security --all-features`; `cargo build -p hello`; `graphify update .`.

## Risks

- The registration model changes under every existing path. The existing tests are the regression net, plus a characterization of build order written before the refactor.
- Arity-generic code can produce hard-to-read compiler errors. A compile-fail test pins the message for a non-injectable parameter type.
- Lazy creation and shutdown concurrency is the subtle part; it gets its own plan task and the most tests.
- The `#[configuration]` macro only reads method signatures and wraps calls, but its spans and messages need care.
- The module split grows `oxbloom-di` several-fold; the layout keeps each file under about 500 lines of production code.

## Open items

- Dependencies on a bean from another thread while it is being created lazily wait on the container lock; a configurable timeout is not planned.
- Conditions beyond profiles (on property, on bean, on missing bean) arrive with slice C4.
- A collection `App::controllers(&container)` in `oxbloom-web` would follow from `Vec<Arc<dyn Controller>>`; not part of this slice.
