# ADR 0097: Data migrations run `sqlx::migrate` at startup, with its files and history table, fixed error text and no `validate-checksums`

- **Status:** Accepted
- **Date:** 2026-11-25
- **Source:** the data migrations design spec `2026-11-25-data-migrations-design.md` (a local file, not linked), its plan `2026-11-25-data-migrations.md` and the implementation of that plan

## Context

ADR 0096 gave Oxbloom pooled SQL access and left schema migrations out. An application that stores data needs its schema to match its code when it starts, on any of the three supported databases, with two instances that may start at the same time, and without SQL or connection details in an error or a log. This ADR covers M3b, the migrations.

## Decision

**The engine is `sqlx::migrate`.** `oxbloom-data` already depends on `sqlx`, the migration engine supports PostgreSQL, MySQL and SQLite, and its file format and history table are the ones `sqlx-cli` uses, so an application can move between Oxbloom and `sqlx-cli` without converting anything. A second engine would have meant a second file format and a second history table. The runner lives in `oxbloom_data::migrate` behind the cargo feature `migrate` of `oxbloom-data` (`data-migrate` in `oxbloom-boot`), which enables the `migrate` feature of `sqlx`.

**Files: a directory or an embedded migrator.** `data.migrations.path` (and `data.sources.<name>.migrations.path`) names a directory that is read at startup. Alternatively the application embeds its files with `sqlx::migrate!("./migrations")` and registers them in an `EmbeddedMigrations` bean, per source name (`default` for the unnamed keys). When both exist, the `path` wins and one `info` event that names only the source says so. `enabled = true` with neither is a startup error. The macro expands to `::sqlx`, so an application that embeds needs its own direct dependency named `sqlx` with the features `macros` and `migrate`; going through `oxbloom_data::sqlx` is not enough. Oxbloom turns on neither feature of `sqlx` for the application, the same rule as in ADR 0096.

**The lifecycle position is `DataService::start`.** The migrations run after the connectivity ping and before the service reports started, so every service with a later phase sees the migrated schema. `DataService` has the lowest phase, which already made it the first service. Sources are migrated one after the other, the default source first; a failure stops the run and fails the boot. Running the sources concurrently is parked. A source that migrates is connected and migrated even when `data.connect-on-startup` is `false`, because an application that asks for its schema expects it to exist; the other sources stay lazy. The service is registered when there is a source to connect or to migrate. A migrations table without a `url` is still a configuration error naming `data.url`, and `migrations.enabled = false` alone does not register the service.

**Locking.** On PostgreSQL and MySQL the runner uses the advisory lock of `sqlx`, which makes two instances that start together apply each migration once. `locking = false` is for a database without advisory locks, such as CockroachDB. On SQLite the `sqlx` lock does nothing, and a probe showed that concurrent runners on one database file fail with `table already exists`. The runner therefore does two things on SQLite. When `locking` is true it takes the write lock of the database (`BEGIN IMMEDIATE`) for the run, and a migration marked `-- no-transaction` skips that lock. After a failure other than a dirty history or a changed file it runs once more, because a second run is idempotent and sees what the winner applied; a script that really fails fails again and is reported. The write lock cost is that a long SQLite migration blocks every other writer, and a second instance can hit the busy timeout of SQLite. The lock cut the failures of the re-run alone, which hit a small share of rounds, to none in a long stress run.

**The MySQL caveat.** MySQL commits schema changes implicitly, so a script that fails midway stays partly applied and the history keeps a dirty row. The next start fails with the dirty-history report, and the operator has to repair the database. PostgreSQL and SQLite run a script in a transaction, unless it is marked `-- no-transaction`. The guide advises one statement per file where possible.

**`validate-checksums` was dropped.** The spec had a key to switch the check off. `sqlx` 0.9.1 compares checksums inside its run function with no public switch, and the only workaround rewrites the checksums of the migrator before the run, which hides a real change from the engine. A key that has to lie to the engine is worse than no key, so a changed applied file always fails the run. `ignore-missing` is kept, because `sqlx` has a public switch for it. A revert is different: `sqlx` undo checks for missing files and not for checksums, so a changed file does not fail `revert`.

**A dedicated connection with statement logging off.** `sqlx` logs the text of every statement at debug level and of a slow statement at warn level, and a migration script is the statement. A probe with a marker in the SQL showed it in the log. Both `run` and `revert` therefore open a connection of their own with statement logging switched off, so SQL never reaches the logs of `sqlx`. The cost is a second connection while the pool is idle, and on SQLite a pool connection that stays held meanwhile. This is also why a SQLite source with a private-cache in-memory database (`sqlite://?mode=memory` without a name, or `cache=private`) is refused with `MigrateError::PrivateMemory` naming the source: the dedicated connection would open a different, empty database, and running on the pool connection would switch statement logging back on. `:memory:` and a named shared-cache memory database work, and `TestDatabase::sqlite()` uses the latter.

**Error text is fixed.** The `Display` of `MigrateError` is fixed per variant and names the source, and the version and description where a single migration is at fault. It never holds SQL, a file path or the URL, because `sqlx` error text can hold all three and names the default history table even for a custom one. The `sqlx` error stays available through `source()` for code that must look at it. The boot failure report adds the key to change and, for a dirty history, what it means on that database.

**The run and revert functions depend on `sqlx` internals.** `Migrator::run` on a connection does not return a `Send` future, so the runner calls the public but hidden `Migrator::run_direct`, and `revert` goes through an `undo_direct` that mirrors the code of `sqlx` 0.9.1 on the public `Migrate` trait. Both must be kept in step when `sqlx` is upgraded. The build matrix of the cargo features and the migration conformance suite on the three databases are what catch a drift.

**The timeout does not cancel.** `timeout` bounds the whole run including the wait for the lock. When it passes, the runner stops waiting and closes its connection, but it does not cancel the statement that is running: on PostgreSQL the backend keeps the advisory lock until the script ends, on SQLite the statement keeps the write lock, and on MySQL the following run can wait. Cancelling is different per driver (`pg_cancel_backend`, `KILL QUERY`, the SQLite interrupt call) and is not simple to get right, and after a timeout the boot fails and the process ends anyway. A restart right after a timeout can still wait for the old statement. This is documented and not fixed.

**Concurrent runners on SQLite.** Two application instances can share only a database file. Concurrent runners on one shared-cache in-memory database inside one process are not supported: they can fail with SQLite code 262 (`SQLITE_LOCKED_SHAREDCACHE`), which the busy timeout does not cover, frequently. Each migration is still applied exactly once, but the reports of concurrent runners can overlap, because each reads the history before it takes the lock.

**The history table name.** `table` is validated (`[A-Za-z_][A-Za-z0-9_]*`, at most 63 characters) because it is placed in SQL, and checked again where it is used. `sqlx` offers the change only through `dangerous_set_table_name`: renaming the table of an existing database needs a copy of its contents first. PostgreSQL folds an unquoted name to lower case, and `sqlx` creates the table unquoted, so a custom name behaves case-insensitively there. The health indicator had to respect this: it asked for the quoted capitals name and found nothing.

**Health.** The `DataHealthIndicator` of a migrating source adds the detail `migrations`, the highest version recorded as successfully applied, as a number, and leaves it out when the history table does not exist. It never shows a description or SQL.

**Test support.** `oxbloom-test` has `MigrationFiles` (a temporary directory with `up`, `reversible` and `plain` files), `TestDatabase::with_migrations(dir)` and `config_snippet_with_migrations(dir)`. The migration conformance suite runs on SQLite always and on PostgreSQL and MySQL under `make test-db`. Running it on real servers found two defects that the SQLite tests could not: the capitals history table on PostgreSQL, and a failing down script on MySQL that was reported without its version. `make test-db` now runs every test binary even when one fails.

## Consequences

- An application sets `data.migrations.enabled` and a `path`, or registers an `EmbeddedMigrations` bean, and has its schema at start. Without the cargo feature, `enabled = true` fails the start with a report that names the feature.
- Files and history are compatible with `sqlx-cli`, which remains the tool for creating, running and reverting by hand.
- A changed applied file cannot be tolerated by a setting; the application adds a new migration instead.
- On MySQL a failed migration needs a manual repair. On SQLite a long migration holds the write lock.
- A timed-out statement keeps running, and with it its lock, until it ends.
- `run_direct` and `undo_direct` must be checked at every `sqlx` upgrade.
- `revert` is a function for applications and tools. Boot never calls it, and there is no automatic down migration.
- Parked: repeatable and Flyway-style scripts, a baseline, automatic down migration, a command line tool (use `sqlx-cli`), concurrent migration of several sources, a dry run, profiles, a lock timeout other than `timeout`, and the cancellation of a timed-out statement.
