# ADR 0096: The data core is `sqlx` with pools as beans, explicit transactions and fixed error text

- **Status:** Accepted
- **Date:** 2026-11-25
- **Source:** the data core design spec `2026-11-24-data-core-design.md` (a local file, not linked), its plan `2026-11-24-data-core.md` and its Tasks 1 to 9

## Context

An Oxbloom application that stores data needs pooled connections to a SQL database, a way to run work in a transaction, a health check, TLS to the server that reuses the SSL bundles, and a way to test against a real server. The module list in `docs/ROADMAP-modules.md` names this M3. This ADR covers M3a, the first part: connections, pools, transactions, health and tests. Schema migrations are M3b and are not part of this decision.

## Decision

**The toolkit is `sqlx` 0.9.1.** It supports PostgreSQL, MySQL (and MariaDB) and SQLite with one pool type per driver, runs on Tokio, needs no code generation and has a rustls TLS option. `oxbloom-data` re-exports it as `oxbloom_data::sqlx`, so an application uses the same version as the framework. The crate sets `default-features = false` and enables `runtime-tokio` only. The migrate and macros features of `sqlx` are left to the application. `sqlx` 0.9 declares `rust-version` 1.94, which fits the workspace MSRV (1.99).

**The TLS roots choice is `tls-rustls-aws-lc-rs-native-roots`.** Oxbloom already uses rustls on `aws-lc-rs` everywhere (ADR 0068), and the workspace has no `ring`. Task 1 checked `cargo tree -i ring -p oxbloom-data --all-features` and it prints nothing. The `native-roots` variant uses the platform certificate store, so a server with a certificate from a public or a company CA works without configuration. The rustls feature is attached to the driver features (`postgres`, `mysql`, `sqlite`), not to the crate, so a build without a driver has no TLS crates at all; with it unconditional the build pulled nine more crates, rustls, `aws-lc-rs` and `webpki` among them.

**Cargo features.** `postgres`, `mysql` and `sqlite` each enable the matching `sqlx` driver, and none is on by default. `retry` adds `transaction_with_retry` (see below). In `oxbloom-boot` the features `data-postgres`, `data-mysql` and `data-sqlite` enable `oxbloom-data` with the driver and with `retry`, and `oxbloom-actuator/data` when the actuator feature is on. There is no separate `data` feature in boot, so an application that wants a database names the driver it uses.

**Pools are beans, built from a registry.** The `data.*` keys describe one default source (the unnamed keys) and any number of named sources under `data.sources.<name>`. `DataSources` is the registry: it builds one lazy `sqlx` pool per source and offers `postgres(name)`, `mysql(name)` and `sqlite(name)` (each behind its driver feature), plus `names`, `default_name`, `driver_of`, `ping`, `ping_all`, `pool_counts` and `close_all`. With a `data` section, `DataAutoConfiguration` registers the `DataSettings`, the `DataSources` and the `DataService`, and the default source also becomes a bean of its pool type (`PgPool`, `MySqlPool` or `SqlitePool`, injected as `Arc<..>`). The default pool bean backs off when the application registers its own bean of that type (`on_missing_bean`). Named sources are reached through the `DataSources` bean.

**A registry instead of qualifiers.** The container has no qualifier mechanism (see the DI limits), and it cannot register a bean per source name from configuration. Giving each named source its own bean type would force an application to know the names at compile time. A single `DataSources` bean looked up by name keeps wiring simple and works with the existing container. A qualifier mechanism may replace this later without changing the registry.

**No query API.** `oxbloom-data` adds no query builder, mapper or repository layer. The application uses `sqlx` directly (`sqlx::query`, `query_scalar`, `FromRow`). The module owns what the framework should own: configuration, lifecycle, TLS, transactions, health and test support.

**Lazy pool plus a connecting service.** A pool is built lazily, so building the registry opens no connection and needs no database; this keeps bean creation fast and lets a unit test boot without a server. Lazy pools need a Tokio runtime, because `sqlx` ties the maintenance task of a pool to the runtime that is current when it is built; `DataSources::build` outside one fails with `DataError::Pool`. Bean creation runs on the application's runtime. `DataService` is a boot `Service` with phase `i32::MIN` and the lowest DI order, so it starts before every other service and stops after them. With `data.connect-on-startup` (default `true`), `start` pings every source with a 10 second timeout each. An unreachable server ends as a pool timeout (`sqlx` retries a refused connection until the `acquire-timeout`), which the failure report treats as unreachable, so with the default `acquire-timeout` of 30 seconds the start waits the full 10 seconds per unreachable source. `stop` closes every pool with a 10 second timeout and, when it runs out, logs a fixed warning at target `oxbloom::data` that lists the source names. A failed `start` does not call `stop`; the pools are dropped with the container. When an application registers its own `DataSources` bean there is no back-off for it: the default pool bean and the service use whichever bean the container resolves.

**Errors have fixed text and secrets never leave.** `DataError` has the variants `Config`, `Connect`, `Pool`, `Unsupported` and `Tls`, none with a payload. `DataSources::build` returns a `SourceError` that names the source and gives its configuration key (`data` or `data.sources.<name>`) through `config_prefix()`; its `Display` is "data source `<name>`: <fixed text>". The URL, the password, the user, the host and SQLite paths never appear in an error, in `Debug`, in a log event or in health details; the `url` setting is a `Secret`. The startup report texts are fixed too. One hazard is outside our control: `sqlx`'s own `Debug` of `connect_options()` of a pool includes the password, so that value must never be logged, and the docs say so on every pool accessor.

**Explicit transactions and savepoints.** `transaction(&pool, &TransactionOptions, async |tx| ..)` takes a pool of any enabled driver and an async closure that gets `&mut sqlx::Transaction`. It commits on `Ok` and rolls back on `Err`, on a panic of the closure and when the returned future is dropped (the `sqlx` transaction queues a rollback on drop). There are no ambient transactions: no task-local current transaction, no annotation. A nested unit of work uses `tx.begin()`, which creates a savepoint. `TransactionError<E>` has `Begin`, `Commit`, `Unsupported` and `Inner(E)`; its `Display` is fixed and its `Debug` prints only the variant name, so no driver text, SQL or row data reaches a log. The closure bound is `for<'t, 'c> AsyncFnMut(&'t mut Transaction<'c, DB>)`, not `Transaction<'static, DB>`, because with `'static` a closure inside `tokio::spawn` failed with an "implementation of `AsyncFnMut` is not general enough" error. Because of the compiler limitation rust-lang/rust#110338, the future is not `Send` when the closure borrows from the surrounding code. Inside `tokio::spawn` or a web handler the closure is written as `async move` over owned data.

**Per-driver options and their refusal.** `TransactionOptions` has an isolation level and a read-only flag. PostgreSQL runs `BEGIN ISOLATION LEVEL .. READ ONLY`. MySQL runs `SET TRANSACTION ISOLATION LEVEL ..` and `START TRANSACTION READ ONLY` as one statement through `begin_with`; the connection negotiates multiple statements, and the begin was verified against a live MySQL 8.4 server in Task 9. SQLite transactions are always serializable and cannot be read-only, so a SQLite pool accepts only the default and `Serializable` and refuses everything else with `TransactionError::Unsupported` before it acquires a connection. An option that a driver cannot honor is refused, never ignored.

**`retry` is additive and has its own loop.** Cargo features merge across a build, so a feature that adds a bound to `transaction` would break callers that did not ask for it. `transaction` therefore has one signature in every configuration. With the feature `retry`, `transaction_with_retry(&pool, &options, &policy, work)` runs the work again, in a new transaction, after a serialization failure or a deadlock, following an `oxbloom_tasks::RetryPolicy`. The error type of the work must implement the public trait `RetryableError`, which `sqlx::Error`, a boxed error with a `sqlx::Error` in its source chain and `TransactionError<E>` implement; an application error that wraps `sqlx::Error` delegates to it. The classification is PostgreSQL SQLSTATE `40001` and `40P01`, MySQL errors `1213` and `1205`, and the SQLite primary result codes `SQLITE_BUSY` and `SQLITE_LOCKED`. The retry loop is its own, not `RetryPolicy::run`, for two reasons: `run` logs the error text of every failed attempt, which could put SQL fragments and server text into logs, and it cannot lend a mutable `AsyncFnMut` closure to a new future per attempt. The loop uses `policy.delay(attempt, fastrand::f64())` and `tokio::time::sleep`, logs nothing and returns the last error. The closure must be idempotent: the database work is rolled back, but effects outside the database are not. SQLite reports `SQLITE_LOCKED` also for a conflict within one connection, which fails the same way on every run, so it is retried until the attempts run out.

**In-memory SQLite is special.** Closing the last connection of an in-memory database destroys it. A source with an in-memory SQLite URL therefore gets one connection by default, an explicit `max-connections` above 1 is refused unless the URL has `cache=shared`, and `idle-timeout` and `max-lifetime` default to none. A user-set `idle-timeout` or `max-lifetime` can still destroy a non-shared in-memory database; this is documented, not refused. `TestDatabase::sqlite()` uses a unique shared-cache database name and keeps one connection open for its lifetime. `min-connections` on a lazy pool is honored only loosely, because `sqlx` opens and refills those connections in the background.

**TLS comes from SSL bundles, and `ssl-bundle` means `verify-full` (ruling R4).** A source can name an SSL bundle in `ssl-bundle` for PostgreSQL and MySQL. With a bundle and no `ssl-mode`, the mode is `verify-full` (MySQL `VerifyIdentity`), which overrides a mode in the URL and `PGSSLMODE`, because a bundle means "check the server against this trust". An explicit `ssl-mode` wins; `prefer` and `require` encrypt but do not check the certificate against the bundle's trust. `ssl-bundle` together with `ssl-mode = disable` is a settings error (R6). A bundle that holds only a client certificate and no `ssl-mode` also defaults to `verify-full`, against the platform roots; a server behind a private CA then needs the CA in the bundle's trust or an explicit `ssl-mode`. `ssl-mode` and `ssl-bundle` are errors for a SQLite source. Pools keep the PEM they were built with and do not follow a reload of the bundle. The PEM is parsed on the first connection, so a bad PEM shows up as `DataError::Connect` then.

**PEM accessors in `oxbloom-ssl`.** `sqlx` takes PEM, while a bundle holds parsed material, so `SslBundle::trust_pem()` returns the trust certificates and `SslBundle::identity_pem()` returns the chain and the private key, both as PEM bytes. The key keeps its own encoding under the matching label: `PRIVATE KEY` for PKCS#8, `RSA PRIVATE KEY` for PKCS#1 and `EC PRIVATE KEY` for SEC1. `sqlx` with rustls reads all three; `native-tls` would need PKCS#8, but Oxbloom does not use it. The encoding uses `pem-rfc7468`, which was already in the tree. The key bytes are a plain `Vec<u8>`: callers must not log them. The bundle now also keeps the DER of its trust certificates and its key, which are needed to produce the PEM.

**Health.** `DataHealthIndicator` (feature `data` of `oxbloom-actuator`) is named `db` for the default source and `db.<name>` for a named one, with the details `driver`, `size` and `idle` when up. A down source shows `connection failed` or `timed out` after a 3 second timeout; a pool error after the whole timeout counts as `timed out`, and every other failure as `connection failed`. The container cannot register a bean per source name, so `ActuatorAutoConfiguration` builds all indicators in one `DataIndicators` bean and chains them after the `dyn HealthIndicator` beans in the health runner. An application that collects the `dyn HealthIndicator` beans itself does not see them. Readiness `include` accepts the names.

**Test strategy with env-gated servers.** `TestDatabase` in `oxbloom-test` (feature `data`, plus `data-postgres` and `data-mysql`) gives a throwaway database: an in-memory SQLite database always, and a uniquely named `oxbloom_test_*` database on the server named by `OXBLOOM_TEST_POSTGRES_URL` or `OXBLOOM_TEST_MYSQL_URL`. The per-driver conformance suite (tests named `data_conformance_*`) lives in `crates/oxbloom-test/tests/`, not in `oxbloom-data`, because a dev-dependency of `oxbloom-data` on `oxbloom-test` would turn on `sqlite` and `retry` in every test build of `oxbloom-data` and stop the builds without a driver from being tested. The SQLite tests always run; the PostgreSQL and MySQL tests are `#[ignore]`d. `make test-db` starts PostgreSQL 17 on 127.0.0.1:55432 and MySQL 8.4 on 127.0.0.1:53306 from `compose.test.yaml` (both on tmpfs), exports the two URLs, runs the ignored tests and removes the containers with `down -v`. A test that panics before `close` leaks its database on a persistent server.

## Consequences

- An application chooses its driver features and writes plain `sqlx` queries; the framework supplies pools, TLS, transactions, health and shutdown.
- Named sources are looked up by name on the `DataSources` bean and are not injectable by type; the default source is.
- There are no migrations (M3b is next), no ambient transactions, no repository layer, no qualifier mechanism, no pools that follow bundle reloads, and no database other than PostgreSQL, MySQL and SQLite.
- The `Send` limitation of borrowing closures is a compiler issue; the docs show the `async move` form.
- A failed health check shows only a fixed text. The cause is not logged by the indicator, so diagnosing needs the application's own logs at the place where the pool is used.
- The retry loop duplicates a little of the policy logic of `oxbloom-tasks` (the attempt count and the delay) to keep error text out of the logs.
- `oxbloom-test` gained dev-dependencies on `oxbloom-boot` (with `actuator`), `oxbloom-actuator` (with `data`) and `oxbloom-tasks`, which unify into every test build of `oxbloom-test`; the stack probes of `oxbloom-boot` did not change (238 KB passes and 237 KB overflows; 239 KB and 238 KB with all features).
- The MySQL isolation check of the conformance suite reads `information_schema.innodb_trx`, which needs the `PROCESS` privilege, so a restricted `OXBLOOM_TEST_MYSQL_URL` user fails that test.
