# ADR 0095: The OAuth2 client caches one access token per registration and coalesces the requests that ask for it

- **Status:** Accepted
- **Date:** 2026-11-24
- **Source:** the security Slice 9 design spec `2026-11-23-oauth2-design.md`, part C (a local file, not linked), its plan `2026-11-23-oauth2.md`, Tasks 11 and 12

## Context

An application that calls a protected service as itself, not on behalf of a user, needs an access token from the client credentials grant. Asking the provider on every call is slow and may be rate limited, and caching a token naively has three traps: many callers can find the token stale at the same moment and each ask for a new one, a failed request must not poison the cache, and a provider may send a lifetime of zero or none at all.

## Decision

**`OAuth2Client` holds one token per registration.** `OAuth2Client::client_credentials(registration_id)` returns the cached token until a skew (default 30 seconds) before its expiry and requests a new one after that. The client reads the registrations and providers of `OAuth2Settings` and resolves the provider metadata through a `MetadataCache`, the same type as the login uses but its own instance (ruling R23): `OAuth2Client::new` creates one and `OAuth2Login` another, so an application with both the login and the client discovers each provider twice per hour. Sharing one instance is parked. Discovery keeps the 5 second failure backoff of `MetadataCache`, so within 5 seconds of a failed discovery a call can return `TokenError::Discovery` or `Http` without any request; the token request itself has no backoff. Time comes from `oxbloom_core::Clock`, so tests use `ManualClock`.

**One request at a time per registration.** Each registration has a slot with an async lock that is held while the request is in flight. Callers that arrive meanwhile wait for the lock and take the outcome of that request, a token or a failure, instead of starting their own. A failure is shared with the callers that waited for it but is not kept: the next caller that arrives later makes a new request at once. This avoids a queue of one timed-out request per caller during an outage, and no backoff is needed here because a caller asks only when it needs a token. Slots exist only for configured registration ids, so an unknown id cannot grow the map.

**Lifetimes.** A token without `expires_in` counts as valid for 60 seconds. The expiry is computed with `TokenResponse::expires_at`, which cannot overflow. A token that is within the skew of its expiry when it arrives, including one with `expires_in = 0`, is returned to the callers that waited for that request but is not stored, so one call never loops and the next call asks again.

**`invalidate` and `invalidate_token` (ruling R22).** Both bump a generation counter of the slot, which makes the stored token unusable at once without waiting for an in-flight request; a token whose request started before the bump is not stored. The usable token sits behind a plain mutex that is never held across an await, so both are synchronous and can look at the token while a request is in flight. `invalidate(id)` is the unconditional reset. `invalidate_token(id, refused)` acts only if the stored token equals the refused one (same expiry, constant-time equal value), so a late 401 for an old token cannot discard a fresh one, and N callers refused with the same token cause one refetch between them. `BearerRetryClient` uses `invalidate_token` (see below).

**A public client cannot use this grant.** A registration with `client-authentication = none` is refused with `TokenError::Invalid` before any request: a public client has no secret, and an unauthenticated client credentials request would hand a token to anyone who knows the client id.

**Errors have fixed text.** `TokenError` is non-exhaustive and carries no URL, body or token. The provider's error code is surfaced only when it is one of the RFC 6749 section 5.2 codes (the same allow-list as the login), and is `unknown` otherwise; the `error_description` is never read. `AccessToken` hides the token in `Debug`.

### User tokens and the bearer interceptors (Task 12)

**User tokens are request-based.** `OAuth2Client::access_token_for(&request, registration_id)` reads the token set that the OAuth2 login stored in the session of the request (`StoredTokens`, one per registration). Sessions are request-scoped, so there is no call that takes a user id, and there is no persistent token store of the client: the session is the only place a user's tokens live, and they end with it. `UserTokenInterceptor::for_request` takes the session handle and the authentication of one request at construction and is built per request.

**The current authentication must be the OAuth2 login of the registration (binding ledger requirement).** `access_token_for` refuses with `TokenError::ReauthenticationRequired`, before it looks at the session, unless the authentication of the request has `oauth2.principal = true` (the boolean) and `oauth2.registration` equal to the requested id. Tokens can outlive a later password login in the same session; the login also clears the tokens at every other login, and this check is the second line of defense, so a token never reaches a principal it was not issued to. Provider attributes named `oauth2.*` are dropped at the login, so a provider cannot forge the markers.

**Refresh.** A token is used until its expiry minus the skew; a token stored without an expiry (no `expires_in` at the login, as with GitHub OAuth apps, which also issue no refresh token) is used as it is, because refusing it would make such providers unusable. A due token is refreshed with `grant_type=refresh_token` and no `scope` (RFC 6749 section 6: the scope of the login), with the client authentication of the registration; a public client may refresh with its `client_id` alone, unlike the client credentials grant, because the refresh token itself is the credential. The new refresh token replaces the old one, a missing one keeps it, and the id token and scope of the login are kept (a new id token from a refresh is not validated, so it is not stored). A missing `expires_in` counts as 60 seconds, as for client credentials; `expires_in = 0` gives a token that is returned once and refreshed again on the next call, so one call makes at most one request. `invalid_grant` removes the tokens and asks for a new login, as does a due token without a refresh token; every other failure leaves the tokens untouched, so a provider outage does not log the user out.

**Refreshes are serialized per session and registration.** A provider that rotates refresh tokens refuses a spent one with `invalid_grant`, so two concurrent refreshes with the same refresh token would log the user out. The client keeps one async lock per session id and registration. Concurrent requests of one session each load their own copy of the session, so the lock also remembers the last refresh made under it: the refresh token it spent and the tokens it stored. A call that waited and still holds the spent refresh token (compared in constant time) takes those tokens and stores them in its own session copy instead of refreshing; whichever request is saved last, the session holds the rotated refresh token. Holding the same refresh token is the proof that the tokens belong to this session, so no token crosses sessions even in theory. The lock map is a mutex-protected map of `Weak` entries; the last call to let go of an entry removes it, so the map holds only entries with a call in flight and cannot grow with the number of sessions a client presents. The record of the last refresh lives only as long as its entry.

**Interceptors.** `ClientCredentialsInterceptor` adds the client credentials token and never retries. `BearerRetryClient` wraps an `HttpClient`, adds the same token and, on a 401, drops the answer, calls `invalidate_token` with the refused token (ruling R22: compare-and-invalidate, never the unconditional `invalidate`, so a late 401 cannot discard a fresh token and N refused callers cause one refetch) and sends a clone of the request exactly once more. One retry only: a second 401 with a fresh token means the token is not the problem. The retry also applies to `POST` and other methods that are not idempotent, because a 401 means the service refused the request before processing it; a service that processes a request and then answers 401 must not be put behind this client. `UserTokenInterceptor` never retries, because a refused user token can only be fixed by the user. The interceptor trait returns an `HttpClientError`, so every `TokenError` becomes the fixed-text `HttpClientError::InvalidRequest` (no new variant was added to `oxbloom-http-client`); the `TokenError` is logged at debug level, and callers that need it call `client_credentials` or `access_token_for` first. The `Debug` output of the interceptors shows the registration id only.

## Consequences

- Many tasks can call `client_credentials` freely: they share one token and one request per expiry.
- A token that the resource server refuses before its expiry stays in the cache until the application calls `invalidate_token` (or `invalidate`).
- A token lifetime no longer than the skew means a new request on every call; keep the skew below the lifetime the provider issues. Clamping the skew to the lifetime is parked.
- `AccessToken` is `#[non_exhaustive]` (read its fields, do not build it), and `TokenError` is `Copy`, so a variant that carries non-`Copy` data would be a breaking change (parked).
- The cache is per process and in memory; instances behind a load balancer each ask the provider.
- A slot keeps the outcome of its last request in memory until the next request, so an expired token can stay in memory until then.
- A user's access token is refreshed on the request that needs it, and the session filter stores the new tokens when that request ends. A request of the same session that started before that save and arrives after the lock entry is gone sends the spent refresh token and, with a rotating provider, gets `invalid_grant` and a new login; the window is the time between two overlapping requests of one browser and is accepted.
- Token errors in the interceptors cannot be told apart from an invalid request by type; the debug log and a direct call of the client tell them apart.
- `UserTokenInterceptor` kept past its request finds an empty session and fails every call, by design.
