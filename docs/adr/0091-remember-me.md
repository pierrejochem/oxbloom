# ADR 0091: Remember-me is a stateless signed cookie bound to the password hash, and the session keys of Oxbloom are reserved

- **Status:** Accepted
- **Date:** 2026-11-22
- **Source:** the security Slice 7b design spec `2026-11-22-remember-me-design.md` (a local file, not linked) and its plan

## Context

After Slice 7a a browser user who logs in with a form keeps the login for as long as the session lives, at most the absolute timeout of the session (8 hours by default). A user who closes the browser or comes back the next day logs in again. Many applications let the user choose to stay logged in for days or weeks. How does Oxbloom offer that without a second store, without a second login path that skips the checks of the first, and without weakening the sessions it already has?

Sessions are [ADR 0087](0087-sessions.md), form login is [ADR 0088](0088-form-login.md), CSRF is [ADR 0089](0089-csrf-tokens.md) and session management is [ADR 0090](0090-security-headers-and-session-management.md).

## Decision

**The cookie is a stateless signed token.** The value is `v1.<base64url(username)>.<expiry seconds>.<base64url(HMAC-SHA256)>`. The MAC covers a version tag, the length-prefixed user name, the expiry and `UserDetails::password()`, which is the stored hash string. The key comes from HKDF-SHA256 over the remember-me secret with the info string `oxbloom remember-me v1` and an empty salt, so it never equals the key of the session cookie, which uses another info string. Each comparison is constant time (`hmac::verify`), checking the current key first and then each old key; the number of comparisons shows which key matched, and only for a valid MAC. An expiry that `SystemTime` cannot hold is refused when the token is built, and a token over 1 KiB is refused by `encode` and by the parser. The username is in the cookie in the clear, only base64url encoded, so it is not secret, and the token never holds the password hash.

**The cookie is bound to the password hash.** A changed password changes the stored hash, so every remember-me cookie of that user stops verifying at once, with no list to update. The same holds for a user that is deleted, disabled or locked: auto login loads the user and refuses all three. This is the only revocation there is. The lifetime is fixed: the `Max-Age` equals the lifetime from the moment of issue, and a cookie never extends itself. A login with the box ticked issues a new one. A successful login without the box clears a remember-me cookie that the request carries, because on a shared browser the cookie of the previous user would otherwise log that user in again when the new session idles out; it sets nothing when the request has no such cookie, and a failed login never sets or clears it. A `lifetime` lowered later also applies to cookies already issued: a token whose expiry is beyond now plus the configured lifetime is refused before any user lookup.

**Issuing and clearing.** After a successful password login whose form has the field `security.remember-me.field-name` (default `remember-me`) with the value `on`, `true`, `yes` or `1`, compared without regard to ASCII case, the answer carries the cookie `OXBLOOM_REMEMBER_ME` (`security.remember-me.cookie-name`). It is `HttpOnly` and `SameSite=Lax`. Its `Path` and `Secure` come from the session settings: the session filter stores a `CookieScope` extension on the request with the path and the `Secure` decision of its own cookie, and the remember-me code reads it, so the two cookies cannot disagree. Without a session filter the defaults apply. The cookie name must differ from the session cookie name, or the startup fails with an error that names `security.remember-me.cookie-name`. That check runs only on the boot configuration path: a hand-built `HttpSecurity` or a user-registered `SessionFilter` with its own name is not checked, and on a clash a session cookie that does not parse as a token would get a clearing cookie with the same name, which destroys anonymous sessions. Keep the two names different. A failed login never sets the cookie, and neither does a login whose user the user service cannot load or whose token would be over 1 KiB (one fixed log text each). Logout clears it with `Max-Age=0`. The default login page shows a checkbox with that field name only when remember-me is on.

**Auto login is in the chain, last.** It runs only when the request has no `Authorization` header at all, not even one of an unknown scheme, and when the session gave no authentication, because header credentials win and a session login wins over the cookie. The token is valid when the format parses, the expiry is in the future (checked against the one clock before any lookup), the user exists in the `UserDetailsService`, is enabled and not locked, and the MAC verifies. Then the chain creates or rotates the session, stores the authentication with the marker `remembered`, writes the reserved keys `oxbloom.security.principal` and `oxbloom.security.revalidated-at`, applies the 7a session limit through the same code as a password login, replaces the CSRF token and continues as authenticated. Any invalid cookie gets a clearing `Set-Cookie` and an anonymous request, and the client cannot tell the reasons apart. An error of the user service keeps the cookie and continues anonymous, with one fixed log text. A cookie header over 8 KiB counts as no cookie. Without a session filter there is one fixed log text and no auto login. The check is the free function `check_token` and the login steps are a method of the form login handlers, because the handlers hold the limit, the CSRF settings and the clock.

**The marker.** The `details` of the stored authentication carry `remembered`, and `Authentication::is_remembered()` reads it. A password login stores an authentication without it, so a user who logs in with the password inside a remembered session is fully authenticated again. The new rule `AuthorizationRule::FullyAuthenticated`, built with `RuleBuilder::fully_authenticated()`, grants an authenticated request that is not remembered. Basic and bearer count as fully authenticated. `authenticated()` still accepts remembered users, so an application chooses which paths need a recent password. A JWT whose claims contain `oxbloom.remembered: true` is read as remembered as well. That is deny-only (it can only make `fully_authenticated()` refuse), so it is documented and the converter is not changed.

**The reserved prefix is enforced.** `Session::set` returns the new `SessionError::ReservedKey` for a key that starts with `oxbloom.security.` and writes nothing, and `Session::remove` ignores such a key, so it stays infallible and no caller breaks. `get` stays allowed. Application code can therefore no longer write the authentication, the principal or the remembered marker by accident through `set` and `remove`; the hidden `set_reserved` and a custom `SessionStore` can still write them. Oxbloom's own writers and the integration tests of this repository use the `#[doc(hidden)]` methods `set_reserved` and `remove_reserved`, which guard against accidental collisions and not against hostile code in the same process.

**Settings and configuration.** The keys are `security.remember-me.{enabled, secret, old-secrets, lifetime, field-name, cookie-name}`. It is off by default. The lifetime is 14 days by default, at least 1 minute and at most 365 days. Every secret, current and old, is at least 32 bytes, and the keys are checked even while `enabled` is `false`, so a bad value in a switched-off section still fails the startup. Remember-me needs form login, a secret and a `UserDetailsService` bean, and each missing piece fails the startup with an error that names its key and never a value. The secrets are `Secret` values: no log line, error text, `Debug` output or metadata shows one, and they are never read from the command line. `HttpSecurity::remember_me(|r| ..)` composes, as `headers` does, so a customizer can change one setting and keep the rest. Boot applies remember-me before the customizers and passes the same clock bean to remember-me and to form login. A customizer that calls `http.clock(..)` does not change the clock of remember-me. To rotate the secret, put the new one in `secret` and the old one in `old-secrets`; remove the old one after the longest lifetime has passed. `TestResponse::header_all` in `oxbloom-test` reads a header that occurs several times, such as two `Set-Cookie` lines.

**The split.** Slice 7b is the cookie, the auto login, the marker and the reserved prefix. A persistent token store with per-device revocation and theft detection, a cookie that refreshes, an admin endpoint to revoke remember-me cookies and the 7a deferred minors stay out.

## Consequences

Good:

- A user can stay logged in for days with no state on the server, so the cookie works with both session backends and with several instances that share the secret.
- A changed password, a deleted user, a disabled user and a locked user end every cookie of that user at the next request.
- The cookie cannot be forged without the secret, cannot be moved to another user name, and a cookie of a user whose password changed is dead.
- An application can ask for a recent password on sensitive paths with `fully_authenticated()`.
- Application code can no longer write the authentication, principal or remembered keys of a session by accident through `set` and `remove`.
- The new code writes no secret, token, user name or session id to a log line, an error text, a redirect or `Debug` output.
- The boot stack probes did not grow (238 KB and 239 KB).

Bad:

- There is no per-device revocation and no theft detection. A stolen cookie works until it expires or the password changes, and the owner cannot see or end it. The lifetime is fixed, so a cookie does not extend itself, and a user who wants a new one logs in again with the box ticked.
- The cookie holds the user name in the clear (base64url, not encrypted), so anyone who can read the cookie can read the name. It is `HttpOnly`, but over plain HTTP it is visible on the wire; use TLS.
- An auto login on an unsafe request (`POST`, `PUT`, `PATCH`, `DELETE`) is answered 403, because the new session has a CSRF token that the request cannot know. The next `GET` carries the new session cookie and works. For the same reason a logout `POST` after the session expired, with CSRF on, is 403 and keeps the cookie, until a `GET` has logged the browser in again.
- The `UserDetailsService` must know every user that form login authenticates. A user that another provider authenticates is not found, so the cookie is cleared and the user is anonymous.
- Any `Authorization` header blocks auto login, also one that is not a credential of this application. A browser that sends such a header on every request never gets auto login.
- Log out everywhere (the 7a registry) and the session limit end sessions and do not revoke remember-me. A session that was evicted or ended logs straight back in from the cookie. A burst of parallel requests after the session expired can each auto log in, each create a session and each count against the limit, until the limit evicts the extra ones.
- Revalidation of the session (7a) does not look at the cookie and does not check the password hash, so a changed password does not end an existing session. It ends every remember-me cookie of that user at once. Call `SessionRegistry::invalidate_all` (7a) when a password changes.
- A `fully_authenticated()` rule uses the marker of the session. A JWT claim `oxbloom.remembered: true` makes a bearer request count as remembered.
- Adding the variant `AuthorizationRule::FullyAuthenticated` breaks an exhaustive `match` over that enum in an application. Adding `SessionError::ReservedKey` breaks an exhaustive `match` over `SessionError` the same way.
- A custom login page must post the field `remember-me` (or the configured name) itself. Only the default page has the checkbox.
- A customizer's `http.clock(..)` does not change the clock of remember-me, because boot pins it.
- Remember-me is applied only by `SecurityAutoConfiguration`: an application that defines its own `SecurityFilterChain` bean gets none of the keys, as for form login and CSRF.

## Alternatives considered

- A persistent token store with a series and a token per device, as in Spring Security's persistent token approach: rejected for this slice. It gives per-device revocation and theft detection, and costs a store, a schema and a cleanup. It may come later.
- A cookie that refreshes on use: rejected, because a stolen cookie would then live as long as the thief keeps using it. A fixed lifetime bounds the damage.
- Encrypting the user name in the cookie: rejected, because the MAC already protects it from change and encryption would need a second key and a nonce for a name that is not a secret from the cookie's owner. It is documented as visible.
- Signing with the session key: rejected, because a leak of one use of the key must not give the other. HKDF with its own info string gives separate keys from one secret, and the section has its own secret.
- A marker in a session key that application code could write: rejected, because it could be forged. The reserved prefix is now enforced.
- A `bool` that makes `Session::remove` return an error for a reserved key: rejected, because `remove` has many callers. It ignores reserved keys and says so.
- Making a changed password end sessions as well: rejected for this slice, since the user service does not expose when a password changed. The cookie dies at once; sessions stay until the application ends them with `SessionRegistry::invalidate_all`.
